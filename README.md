# AI PR Review 助手

基于大语言模型的 GitHub Pull Request 代码评审工具，帮助开发者提升 Review 效率与代码质量。

> **核心理念**：不追求发现所有问题，而是用严格的多层过滤机制，让开发者信任每一条输出的风险——"宁可漏报，不要误报"。

---

## 功能概述

| 功能 | 说明 |
|---|---|
| **PR 变更总结** | 自动获取 PR 代码变更，生成结构化摘要（概述、关键变更点、受影响模块、整体风险评估） |
| **风险代码识别** | 多维度识别潜在问题，P0/P1/P2/P3 四级严重度，覆盖安全、性能、逻辑、稳定性、规范五大分类 |
| **Review 建议生成** | 每个风险项附带可直接应用的修复代码（suggestion 字段） |
| **分析模式自适应** | 根据变更量自动切换 trivial / simple / normal / large 四种模式，避免小 PR 过度分析、大 PR 信息遗漏 |
| **逐文件深度分析** | 为每个文件构建独立上下文，按重要性排序后逐个分析，支持跨文件依赖感知 |
| **流式渐进渲染** | SSE (Server-Sent Events) 流式推送，先出总结 → 逐个出风险 → 出元信息，配合进度条实时反馈 |
| **智能缓存机制** | ETag 增量检测 + 本地 JSON 持久化，相同 PR 无新 commit 时直接返回缓存，零 LLM 消耗 |
| **Web 交互界面** | 原生 HTML/CSS/JS（GitHub Dark 风格），支持风险分类筛选、代码语法高亮、P0 风险默认展开 |

## 核心设计亮点

### 1. 多层误报控制体系（⭐ 最大亮点）

传统的 AI 代码评审工具最大痛点是**误报率高**——开发者看到大量噪音后直接忽略全部结果。本系统通过**三层过滤**解决这个问题：

| 过滤层 | 机制 | 作用 |
|---|---|---|
| **第一层：自我反驳** | LLM 输出每个风险前必须自问 3 个问题（"测试文件是否无害？""同类文件是否有相同模式？""旧代码是否已存在？"），三项中任意一项为"是"则不输出 | 从源头减少误报 |
| **第二层：白名单规则** | 预定义 7 类不标记模式（空值惯用写法、日志语句、注释变更、测试文件硬编码、依赖版本号、格式化、配置文件） | 规则级过滤已知误报 |
| **第三层：置信度阈值** | confidence < 0.65 的风险直接丢弃，不展示给用户 | 数值级兜底 |

### 2. Sliding Window 大文件分块（语义边界感知）

不同于简单的字符截断，本系统按 unified diff 的 `@@` hunk 标记切分大文件。每个 `@@` 标记对应一个完整的功能变更（如一个函数），按此边界切分**不会把语义相关的代码从中截断**。单个 hunk 超过预算时才回退到字符截断（极端情况）。

### 3. 四级分析模式自适应

| 模式 | 触发条件 | 策略 | 资源消耗 |
|---|---|---|---|
| **Trivial** | ≤1 文件, ≤10 行 | 仅变更总结，不识别风险 | 极低 |
| **Simple** | ≤3 文件, ≤50 行 | 仅查 P0 级风险 | 低 |
| **Normal** | 其余常规 PR | 完整分析 P0+P1 | 中 |
| **Large** | >30 文件 或 >500 行 | 仅分析前 30 个重要文件，Top 10 风险 | 高 |

### 4. 跨文件依赖感知

分析单个文件时，系统会扫描所有文件中 import/require 语句，自动注入关联提示。例如：文件 A 新增了对 `auth_helper` 的引用，而 `auth_helper.py` 也在本次 PR 中被修改——系统会提示 LLM"请检查接口是否兼容"。

## 模型选择说明

> 本节阐述系统在模型选择上的设计思路，包括候选模型对比、选型决策及切换策略。

### 候选模型对比

在构建本系统时，我们对以下主流大模型进行了评估：

| 模型 | 上下文窗口 | 代码理解 | 中文能力 | 单价 (输入/输出) | 可用性 |
|---|---|---|---|---|---|
| **DeepSeek-V4** (`deepseek-chat`) | 128K | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ¥1/¥2 (百万token) | 国内直连 |
| **GPT-4o** (`gpt-4o`) | 128K | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | $5/$15 | 需代理 |
| **GPT-4o-mini** | 128K | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | $0.15/$0.6 | 需代理 |
| **Claude 3.5 Sonnet** | 200K | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | $3/$15 | 需代理 |
| **通义千问 Qwen-Max** | 32K | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ¥2.4/¥9.6 | 国内直连 |
| **智谱 GLM-4-Plus** | 128K | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ¥5/¥5 | 国内直连 |

### 选型决策：为什么选择 DeepSeek-V3 作为主模型

**1. 代码理解能力**：DeepSeek-V3 在 HumanEval、MBPP 等代码基准测试中表现优异，尤其擅长识别代码中的安全漏洞和逻辑错误——这正是代码评审的核心需求。

**2. 128K 上下文窗口**：中等规模的 PR 通常包含 20-50 个文件、数百行变更。128K 上下文意味着可以将完整 diff + PR 描述 + 分析指令一次性注入，无需粗暴截断。对比通义千问 Qwen-Max 的 32K 窗口，在处理大型 PR 时有明显优势。

**3. 中文 Prompt 理解 + 英文代码分析**：本项目面向中文开发者，Prompt 使用中文编写以提升指令遵循度，而分析对象是英文代码。DeepSeek-V3 在双语混合场景下表现稳定，不会因语言切换导致分析质量下降。

**4. 成本极低**：百万 token 输入仅 ¥1。以一次典型 PR 分析消耗 15K-30K token 计算，单次分析成本约 ¥0.02-0.05。

**5. 国内网络直连**：无需代理即可访问，降低了部署门槛和使用风险。对国内团队而言，这是重要的工程约束。

### 模型切换策略

项目通过 OpenAI 兼容协议实现模型无关设计。只需修改 `.env` 中的两个变量即可切换：

```ini
# 切换至 GPT-4o-mini（轻量 PR 场景，成本更低）
LLM_API_BASE=https://api.openai.com/v1
LLM_MODEL=gpt-4o-mini

# 切换至 Claude 3.5 Sonnet（需要兼容代理，安全分析更强）
LLM_API_BASE=https://your-proxy.com/v1
LLM_MODEL=claude-3-5-sonnet-20241022
```

推荐策略：**日常使用 DeepSeek-V3**，对安全敏感的 PR（如涉及认证/支付/数据持久化）可临时切换至 GPT-4o 或 Claude 3.5 Sonnet 进行双重确认。

## 上下文获取策略

> 本节阐述系统如何将 GitHub PR 的原始数据转化为 LLM 可消费的高质量上下文——这是决定分析准确性的最关键环节。

### 策略总览

```
GitHub PR API
      │
      ├─→ PR 元信息（标题、描述、作者、分支、commit 数）  ─┐
      ├─→ 文件变更列表（每个文件的 unified diff patch）  ─┤
      └─→ 文件元数据（状态、增删行数、文件类型）         ─┤
                                                        ▼
                                                ContextBuilder
                                                        │
                                          ┌─────────────┼─────────────┐
                                          ▼             ▼             ▼
                                    模式判定      文件过滤&排序   Token 预算管理
                                          │             │             │
                                          └─────────────┼─────────────┘
                                                        ▼
                                               结构化上下文文本
```

### 1. 优先级分层

上下文按重要性分为三层，逐层组装：

| 优先级 | 内容 | 预算分配 | 说明 |
|---|---|---|---|
| **第一层（核心）** | 代码 diff | 约 48K tokens | 所有文件的 unified diff，按变更量降序排列 |
| **第二层（辅助）** | 文件总览 | 约 2K tokens | 文件名、状态、增删行数，用于快速定位 |
| **第三层（参考）** | PR 元信息 | 约 2K tokens | 标题、描述（截断至 500 字）、分支信息 |

### 2. Token 预算管理

系统总预算为 **64K tokens**（配置项 `CONTEXT_MAX_TOKENS`），足以覆盖绝大多数 PR 的完整分析需求。分配策略：

- 代码 diff 是分析的核心依据，占预算的绝大部分
- PR 描述仅作参考（开发者写的描述可能不准确），截断至 500 字符
- 文件总览控制在 50 个文件名以内

### 3. Sliding Window 大文件分块

当单文件 diff 超过 **24,000 字符**时，系统不会粗暴截断，而是按 unified diff 的 `@@` hunk 标记进行语义级分块：

```
原始 diff（40,000 字符）
    │
    ▼ 按 @@ 标记切分
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ Chunk 1      │  │ Chunk 2      │  │ Chunk 3      │
│ @@ L10-L25   │  │ @@ L50-L80   │  │ @@ L120-L160 │
│ @@ L30-L45   │  │ @@ L90-L110  │  │              │
│ (22,000 字符) │  │ (18,000 字符) │  │ (3,000 字符) │
└──────────────┘  └──────────────┘  └──────────────┘
```

**为什么按 `@@` 切分而不是按字符截断**：
- `@@` 行标记了变更在源文件中的位置，每个 hunk 通常对应一个完整的函数或代码块
- 按 hunk 边界切分不会把"SQL 注入代码"和"它后面的补救逻辑"分到两个块中
- 块之间保留 2 行重叠，为 LLM 提供连续性上下文
- 只在单个 hunk 本身超过预算时才回退到字符截断（极端情况）

### 4. 跨文件依赖感知

系统会在所有新增/修改行中扫描 import/require/reference 语句，识别跨文件依赖关系。当发现文件 A 引用的模块在本次 PR 中也被修改时，会在文件 A 的分析上下文中注入提示：

> ⚠️ 关联文件变更提示：`src/service.py` 引用了 `src/utils/auth_helper`，而本次 PR 同时修改了 `src/utils/auth_helper.py`。请检查接口是否兼容。

这是简化的文本模式匹配（非 AST 解析），准确度有限但足以覆盖大多数 PR 中的跨文件依赖场景。

### 5. 文件过滤与排序

**智能跳过**：自动排除 17 类无分析价值的文件——构建产物（`*.min.js`）、锁文件（`package-lock.json`）、资源文件（`*.svg`/`*.png`）、二进制等。这些文件的变更不会产生有意义的评审结果，跳过它们既节省 token 又减少噪音。

**重要性排序**：源码文件优先于配置文件，配置文件优先于测试文件，测试文件优先于文档。在 Large 模式下仅分析前 N 个重要文件，确保关键变更不被遗漏。

## 误报与漏报控制

> 这是系统设计中投入最大的环节。代码评审工具的实用性取决于开发者对输出的信任度——宁可漏报 10 个真问题，也不要让开发者因误报过多而关闭工具。

### 三层过滤机制

```
                    ┌──────────────────────┐
   LLM 原始输出 ──→ │  第一层: 自我反驳     │
   (可能含噪音)      │  LLM 自问3问, 过滤    │
                    └─────────┬────────────┘
                              │ 通过
                              ▼
                    ┌──────────────────────┐
                    │  第二层: 白名单规则   │
                    │  7类已知无害模式过滤  │
                    └─────────┬────────────┘
                              │ 通过
                              ▼
                    ┌──────────────────────┐
                    │  第三层: 置信度阈值   │
                    │  confidence ≥ 0.65   │
                    └─────────┬────────────┘
                              │ 通过
                              ▼
                    ┌──────────────────────┐
                    │  最终展示给用户       │
                    └──────────────────────┘
```

### 第一层: 自我反驳 (Self-Rebuttal)

在 Prompt 中要求 LLM 对每个标记的风险执行三项自检：

1. **环境豁免检查**："这段代码在测试文件或开发环境中是否无害？"
2. **同模式检查**："同级目录下其他文件是否有相同的代码模式？"
3. **已有代码检查**："该模式是否在旧代码中已经存在（仅检查新增代码）？"

三项中任意一项为"是"，LLM 必须放弃输出该风险。这个机制利用 LLM 自身的推理能力来做"二次确认"，可以有效过滤掉因上下文不足导致的误判。

### 第二层: 白名单规则

系统预定义了 7 类**不标记**的模式：

| 模式 | 示例 | 理由 |
|---|---|---|
| 空值检查惯用写法 | `if x is None: return` | 防御性编程的标准实践 |
| 日志语句 | `console.log("debug:", data)` | 除非含敏感信息，否则不导致功能问题 |
| 注释/格式化/import 排序 | 仅调整代码布局 | 不影响行为 |
| 测试文件中的硬编码数据 | Mock 对象、固定测试数据 | 测试场景下的有意为之 |
| 配置文件新增普通配置项 | 非敏感配置 | 无代码逻辑风险 |
| 依赖版本号更新 | Dependabot/renovate 自动 PR | 非开发者主动变更 |
| 文档文件变更 | `.md`、`.rst`、`.txt` | 不包含可执行代码 |

### 第三层: 置信度阈值

LLM 必须为每个风险输出一个 `confidence` 值（0-1）。系统丢弃所有 confidence < 0.65 的风险。对于 confidence 在 0.65-0.75 之间的风险，前端以半透明样式展示（表示"不确定，请人工确认"），让开发者自行判断。

### 漏报控制策略

在控制误报的同时，系统通过以下设计减少漏报：

- **逐文件独立分析**而非整体 diff 一次分析，确保每个文件都获得 LLM 的充分注意力
- **Sliding Window 分块**确保大文件不被截断遗漏
- **跨文件依赖感知**捕获因函数签名变更导致的兼容性问题（单看一个文件看不出来）
- **测试文件中的 Bug**（`tests/test_bugs.py`）包含 6 类经典缺陷，可作为回归验证基准

## 原创功能模块说明

本项目所有核心业务逻辑均为独立原创实现，未直接复用任何现有代码评审工具（如 CodeRabbit、PR-Agent 等）。各模块原创设计如下：

| 模块 | 文件 | 原创设计要点 |
|---|---|---|
| 配置管理 | `backend/config.py` | 五层配置模型（GitHub/LLM/Context/Storage/App），支持 .env → 环境变量 → 默认值的优先级链 |
| 数据模型 | `backend/models/schemas.py` | 完整定义 PR 数据、四级风险项、变更总结、分析结果的 Pydantic 结构，含 confidence 阈值验证 |
| GitHub 集成 | `backend/services/github_service.py` | URL 正则解析、分页自动拉取、自动重试+指数退避、Rate Limit 友好提示、ETag 增量检测 |
| 上下文构建 | `backend/utils/context_builder.py` | 四模式自动判定、Token 预算分层管理、Sliding Window 按 @@ hunk 分块、跨文件依赖感知、17 类文件跳过规则 |
| LLM 分析管道 | `backend/services/llm_service.py` | 两阶段分析 Pipeline（总结→逐文件风险识别）、自我反驳 Prompt 工程、白名单误报控制、安全 JSON 解析、SSE 流式生成器 |
| 结果持久化 | `backend/services/review_store.py` | ETag 增量缓存索引、原子写入防中断、按 PR URL 快速查找、历史列表查询 |
| API 路由 | `backend/routers/review.py` | FastAPI 路由编排（健康检查/缓存预检/非流式分析/SSE 流式分析/历史列表/详情查询），友好的错误消息映射 |
| Web 界面 | `frontend/` | 原生 HTML/CSS/JS（GitHub Dark 风格），零前端框架依赖，支持 SSE 渐进渲染、风险分类筛选、代码语法高亮 |

## 快速开始

```bash
# 1. 配置环境变量
cp .env.example .env
# 编辑 .env，填入 LLM_API_KEY、 GITHUB_TOKEN 

# 2. 启动
docker compose -f docker/docker-compose.yml up -d

# 3. 访问
# 本地 Docker:     http://localhost:8000
# GitHub Codespaces: 系统自动生成公网 URL（8000 端口）
```

### 方式二：Python 直接运行

- Python 3.10+
- Git
- （可选）GitHub Personal Access Token，用于私有仓库或提高 API Rate Limit

```bash
cd AI-PR-Review
pip install -r backend/requirements.txt
```

#### 3. 配置环境变量

```bash
cp .env.example .env
```

编辑 `.env`，填入 LLM API 密钥：

```ini
LLM_API_BASE=https://api.deepseek.com/v1   # 或其他兼容 OpenAI 协议的服务
```

```bash
cd backend
python main.py
```

服务启动后，访问 `http://localhost:8000`，输入任意 GitHub PR URL 即可开始分析。

### Demo 验证

项目内置了含 6 类故意注入缺陷的测试文件 `tests/test_bugs.py`，可作为系统能力的自测验证基准：

| Bug 类型 | 严重度 | 描述 |
|---|---|---|
| SQL 注入 | P0 安全 | 字符串拼接构造 SQL，缺少参数化查询 |
| 硬编码密钥 | P0 安全 | API Key、数据库密码、加密盐值写死代码中 |
| 不安全加密 | P0 安全 | MD5 + 固定 salt，应使用 bcrypt/argon2 |
| 资源泄露 | P1 稳定性 | 文件/连接打开后无对应的 close/release |
| 无限循环 | P1 逻辑 | 退出条件永远不满足的 while 循环 |
| N+1 查询 | P2 性能 | 循环内逐条执行数据库查询 |

你可以创建一个包含此文件的测试 PR，验证系统的检测准确率。

## API 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/` | 前端 Web 界面 |
| `GET` | `/api/health` | 健康检查 |
| `POST` | `/api/review` | 非流式分析（等待完成后一次返回） |
| `POST` | `/api/review/stream` | SSE 流式分析（渐进推送结果） |
| `POST` | `/api/review/check-cache` | 缓存预检（是否已有分析结果且 PR 未更新） |
| `GET` | `/api/reviews` | 历史分析记录列表 |
| `GET` | `/api/review/{id}` | 指定 Review 详情 |

**请求示例**：

```bash
# 非流式分析
curl -X POST http://localhost:8000/api/review \
  -H "Content-Type: application/json" \
  -d '{"pr_url": "https://github.com/facebook/react/pull/30000"}'

# 缓存预检
curl -X POST http://localhost:8000/api/review/check-cache \
  -H "Content-Type: application/json" \
  -d '{"pr_url": "https://github.com/facebook/react/pull/30000"}'
```

## 未来扩展方向

> 本节说明系统在当前版本之外的设计演进路径，分为三个时间维度。

### 短期（1-2 个月）：工程化与集成

**1. CI/CD 原生集成（GitHub Action / GitLab CI）**
将分析能力封装为 GitHub Action，开发者提交 PR 时自动触发评审，结果以 Comment 形式回写到 PR 页面。开发者在 GitHub 界面内即可完成"提交 → 自动评审 → 查看风险 → 修复"的完整闭环，无需离开代码托管平台。

**2. 多平台扩展**
从 GitHub 扩展至 GitLab、Gitee、Bitbucket 等代码托管平台。核心分析逻辑不变，仅需增加对应平台的 API 适配层。GitHub/GitLab 的 PR/MR 概念高度一致，适配成本低。

### 中期（3-6 个月）：分析深度增强

**3. RAG 知识库增强（项目上下文注入）**
当前分析的上下文仅限于 PR 本身的 diff。引入项目级 RAG 知识库后，可注入以下额外信息：
- 项目架构文档 → 判断变更是否符合架构规范
- 团队编码规范 → 自动标记违反规范的代码
- 历史 Bug 记录 → 识别类似的问题模式
- 函数/类的历史变更记录 → 判断当前修改是否与历史意图矛盾

例如：知识库中记录"所有 Controller 方法必须做权限校验"——当 PR 新增一个未做权限校验的接口时，系统能给出更精准的标记。

**4. 多模型仲裁机制（Cross-Model Verification）**
当前 Single LLM 模式存在单一模型的认知盲区。未来方案：同一段代码同时发送给 2-3 个不同厂商的模型（如 DeepSeek-V3 + GPT-4o + Claude 3.5 Sonnet），取"至少 2 个模型都认为有问题"的风险才输出——类似分布式系统的多数投票（Quorum）机制，进一步降低误报率。

**5. 多语言 AST 深度分析**
当前跨文件依赖分析基于文本模式匹配，准确度有限。引入 Tree-sitter 等通用 AST 解析器后，可以进行：
- 精确的函数签名变更检测
- 调用图构建（Call Graph）→ 真正的依赖影响分析
- 数据流分析 → 发现潜在的未初始化变量、空指针路径

**6. 团队自定义规则引擎**
允许团队定义自己的检测规则（如"所有数据库操作必须带超时"、"禁止在循环中使用 `+` 拼接字符串"），与通用分析结果合并输出。

### 长期（6-12 个月）：智能化与生态

**8. 多轮交互式深度分析（Agentic Review）**
当前是"提交 → 分析 → 返回"的单向流程。未来升级为 Agent 模式：

```
用户: "这个 SQL 注入风险，确认一下项目中还有其他入口存在同样问题吗？"
系统: 检索全量代码 → 发现 3 处相同模式 → 生成专项报告
用户: "帮我给这 3 处全部生成修复 PR"
系统: 生成修复代码 → 创建新 PR → 关联原 PR
```

这是从"评审工具"到"AI Pair Reviewer"的质变。

**9. 代码修复自动生成 PR**
从"发现问题"升级为"修复问题"：P0/P1 风险自动生成修复代码，以新 PR 形式提交给原仓库。开发者只需 Review + Merge 即可完成修复闭环。

**9. IDE 插件生态**
开发 VS Code / JetBrains 插件，将评审能力嵌入编码流程：写代码时实时提示潜在风险，提交前本地预评审，避免问题进入 PR 阶段。
